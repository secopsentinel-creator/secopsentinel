Servicios de automatización: gratis y sin tokens de pago

Los servicios de automatización del proyecto son gratuitos y no dependen de tokens por pago. Toda la inteligencia y la automatización se ejecuta con herramientas locales instaladas en el propio equipo:

  • IA local: Ollama con modelos abiertos. Arquitectura vigente: gemma4:e4b para visión y herramientas, qwen2.5:7b-instruct para extracción de texto y nomic-embed-text para embeddings. Sin APIs de pago ni facturación por consulta.
  • OCR local: Tesseract para español con respaldo de visión de gemma4 en denuncias escaneadas y documentos PDF. PaddleOCR queda como alternativa evaluada, no adoptada en el MVP.
  • Automatización web: Playwright con Chromium local para navegar y descargar expedientes de SECOP II.
  • Búsqueda documental: ChromaDB para indexar y relacionar documentos. Qdrant queda como alternativa futura si crece el volumen.
  • Base de datos: MariaDB 10.4 de XAMPP por socket Unix como almacenamiento del sistema. Los archivos originales no se guardan en la BD: la BD conserva rutas relativas, SHA-256 y metadatos.

Consecuencias directas: costo cero en licencias y tokens, funcionamiento sin conexión a internet durante la operación (salvo la consulta de portales públicos como SECOP II), privacidad total de la información judicial —los documentos no salen del equipo— y escalabilidad sin facturación por uso. La conexión a internet solo se requiere para la instalación inicial, la descarga de modelos/OCR y la consulta de SECOP II. El único costo asociado es el hardware y el consumo eléctrico.

Proyecto

Sistema Inteligente de Apoyo a la Investigación Judicial y Contratación Estatal

Objetivo general

Desarrollar una plataforma web apoyada con Inteligencia Artificial que permita gestionar noticias criminales, analizar documentos, controlar actividades investigativas, automatizar la elaboración de documentos de Policía Judicial e identificar relaciones entre investigaciones, reduciendo significativamente el tiempo de análisis y elaboración de productos investigativos.

Flujo técnico

El núcleo técnico del proyecto es leer el documento de denuncia, alimentar el proyecto con esa información, detectar alertas de delitos, hacer seguimiento a los procesos y automatizar las tareas asociadas. El flujo es el siguiente:

  1. Ingesta del documento de denuncia: carga de PDF, imagen o documento de texto. Se intenta primero la lectura nativa del PDF; si la página está escaneada, el OCR local (Tesseract para español, con respaldo de visión gemma4) extrae el contenido.
  2. Extracción de datos: la IA local identifica personas, identificaciones, entidades, contratos, delitos, fechas y documentos anexos.
  3. Alimentación del proyecto: se crea o actualiza el registro de la OT/NUNC, el expediente digital y la base de datos; el Excel de control investigativo se regenera como exportación.
  4. Detección de alertas de delitos: análisis jurídico inicial, posibles conductas punibles, irregularidades contractuales y señales de riesgo.
  5. Seguimiento de procesos: control de términos, actividades investigativas, oficios enviados y pendientes, respuestas recibidas y estados de gestión.
  6. Automatización: generación de oficios, entrevistas e informes; descarga de documentos de SECOP II con Playwright; actualización automática del dashboard y regeneración del Excel como exportación.
  7. Indexación documental: los documentos se indexan en ChromaDB con nomic-embed-text para búsqueda semántica, relación automática entre casos y consultas tipo Copilot. En el MVP la búsqueda es FULLTEXT en MariaDB.

|-- Respuestas

|-- Informes

Los archivos originales viven en el filesystem, fuera de htdocs. La base de datos guarda la ruta relativa, el SHA-256 y los metadatos del documento; no almacena el binario. El _manifest.json de cada expediente permite verificar integridad y reconstruir vínculos.

Módulo 18 · Generación Automática de Excel de Control Investigativo

Cada vez que se ingresa una nueva OT o se cargan una denuncia y una OPJ, el sistema crea el registro, extrae los datos principales, actualiza el Excel de control, alimenta las estadísticas y crea relaciones automáticas entre procesos.

La fuente de verdad es la base de datos. El Excel es una referencia válida, editable y la principal salida de exportación; no se usa como maestro operativo ni se sincroniza en dos vías. El Excel actual del investigador se importará una sola vez cuando esté disponible y servirá de base para la plantilla de exportación.

Funcionalidad más valiosa

  1. La IA analiza denuncia, OPJ y documentos anexos.
  2. Extrae denunciante, denunciados, entidades, contratos, delitos y testigos.
  3. Actualiza automáticamente el Excel.
  4. Busca coincidencias con todas las OT existentes.
  5. Genera alertas: el denunciado ya aparece en 4 investigaciones; el contrato ya fue mencionado en otra noticia criminal; la empresa registra 7 investigaciones relacionadas; existe otra OT asignada a un fiscal diferente sobre el mismo contratista.

Esta es la arquitectura vigente. Las alternativas evaluadas (React/Next.js, PaddleOCR, Qdrant, Llama 3.2 Vision y DeepSeek) no se adoptan en el MVP. Toda la arquitectura opera con herramientas locales y gratuitas: no requiere APIs de pago ni consumo de tokens facturados. SECOP II es la única fuente externa que requiere conexión a internet durante la operación; la instalación y las descargas iniciales también requieren conexión.

Protección de seguridad y datos judiciales (transversal)

La seguridad es un requisito transversal: se aplica desde la Fase 0 y atraviesa ingesta, OCR, IA, almacenamiento, base de datos, exportaciones, SECOP y respaldos. No se trata como un módulo aislado ni se deja solo para el final. Una inspección de solo lectura del 15 de noviembre de 2026 encontró que Apache y FTP escuchan en todas las interfaces y que el disco raíz aún no tiene cifrado; ambos puntos deben corregirse antes de cargar datos reales.

Controles por capa

Cifrado de datos con LUKS

  • Estado actual: disco raíz ext4 sin LUKS y cryptsetup no instalado.
  • Decisión: contenedor LUKS para ~/.local/share/secopsentinel y para los secretos. Mientras no haya cifrado de disco completo, los permisos 600 no protegen los datos si el disco se extrae.
  • Plan: respaldar y verificar; instalar cryptsetup; crear el contenedor; formatear ext4; montar; migrar datos; actualizar DATA_ROOT y la ubicación de .env; probar la aplicación; guardar la cabecera LUKS y la clave de recuperación en un lugar seguro; documentar el desbloqueo y el montaje.
  • Secretos: el .env debe residir dentro del volumen cifrado o cifrarse aparte con age/GPG. No se acepta una clave de desbloqueo en texto plano sobre el mismo disco.
  • Riesgos: pérdida de la frase o de la clave de recuperación, corrupción del contenedor y error humano al migrar. Mitigación: respaldo verificado, clave de recuperación y prueba de restauración.
  • Aceptación: cryptsetup status muestra el contenedor activo, no hay datos sensibles en texto plano y la aplicación funciona tras desbloquear el volumen.

Firewall y exposición de servicios

  • Política: denegar entrada por defecto; permitir solo loopback; salida permitida a 443/80 para actualizaciones y SECOP, y SSH al equipo de respaldo.
  • Apache: escuchar solo en 127.0.0.1:80 y 127.0.0.1:443.
  • FTP: deshabilitar el servicio en el puerto 21 si no es imprescindible; si se requiere, restringirlo a loopback.
  • Uvicorn: 127.0.0.1:8000. MariaDB: solo socket Unix. Ollama: 127.0.0.1:11434. CUPS: loopback.
  • mDNS/Avahi: evaluar su deshabilitación si no se usa descubrimiento en red.
  • Auditoría: ejecutar con sudo ufw status verbose, nft list ruleset, ss -tulpn e iptables -S. Estas comprobaciones están documentadas, no ejecutadas en esta edición.
  • Aceptación: ss -tulpn no muestra servicios sensibles en 0.0.0.0; el firewall está activo; desde otro equipo de la LAN no se accede a la aplicación.

Autenticación y sesión

  • Login obligatorio de usuario único con contraseña Argon2id y mínimo 12 caracteres.
  • Bloqueo tras 5 intentos fallidos, expiración de sesión y logout real.
  • Cookie HttpOnly, SameSite=Strict y Secure cuando haya HTTPS.
  • Token CSRF en formularios HTMX y límite de intentos en login.
  • Sin MFA por ahora; se documenta como mejora futura.
  • Reset de contraseña por CLI y auditoría de accesos.

Secretos y base de datos

  • .env con permisos 600 dentro del volumen cifrado; .env.example sin valores reales.
  • gitleaks o git-secrets como pre-commit; ningún secreto en el repositorio ni en la bitácora.
  • Usuario MariaDB dedicado con SELECT, INSERT, UPDATE y DELETE solo sobre secopsentinel.
  • No usar root para la aplicación; rotar la clave administrativa.
  • SQLAlchemy con consultas parametrizadas; evitar SQL dinámico.

Archivos, ClamAV y cuarentena

  • Rutas relativas, validación de DATA_ROOT, protección contra path traversal, permisos 600/700 y escritura atómica.
  • SHA-256 al ingerir y verificación al leer; manifiesto por expediente.
  • Validación de MIME, extensión, tamaño, páginas y PDFs cifrados.
  • ClamAV para cargas y descargas SECOP; cuarentena, registro y revisión humana antes de eliminar.
  • OCR y parsers PDF en subproceso con timeout y límites de recursos.

Aplicación web y API

  • Validación con Pydantic y escape automático de Jinja2.
  • Cabeceras de seguridad: CSP, X-Content-Type-Options, X-Frame-Options, Referrer-Policy, Permissions-Policy y Cache-Control: no-store en páginas sensibles.
  • Manejo de errores sin stack traces ni rutas internas; límites de request y rate limiting.

IA y Copilot

  • Todo documento se trata como contenido no confiable; pruebas explícitas de prompt injection.
  • Salida JSON con esquema Pydantic y reintento de reparación.
  • Herramientas del Copilot con allowlist; el modelo no ejecuta acciones arbitrarias.
  • Sin secretos en prompts; redacción de PII en logs; citas a documento y página.
  • Ollama solo en loopback, un trabajo a la vez y timeout.

SECOP y Playwright

  • Perfil de navegador dedicado, fuera del repositorio.
  • Credenciales en keyring o login manual; nunca en código ni logs.
  • Descargas a cuarentena, escaneo con ClamAV y validación antes de moverlas al expediente.
  • Intervención humana para captchas y respeto de términos y límites del portal.

Exportaciones

  • Etiqueta de sensibilidad en DOCX/PDF/XLSX/ZIP y registro de exportaciones.
  • Envío manual y confirmado; sin envío automático en el MVP.
  • Cifrado opcional de ZIP/PDF y borrado seguro de temporales.

Respaldos

  • Destino: segundo equipo con seguridad propia, definido con el área de IT. No se comparten credenciales con la aplicación.
  • Herramienta: por definir con IT. Opciones: restic o borg con repositorio cifrado; alternativa con rsync + tar + gpg ya disponibles.
  • Contenido: dump de MariaDB, expedientes, secretos cifrados, configuración y auditoría.
  • Frecuencia y metas: respaldo diario; RPO propuesto de 24 horas y RTO propuesto de 4 horas; retención definida por el usuario cliente.
  • Verificación: restauración trimestral en directorio aislado, validación de SHA-256 y manifiestos.
  • Aceptación: repositorio cifrado, restauración exitosa y alerta si falla el respaldo.

Auditoría, monitoreo e incidentes

  • audit_log append-only con usuario, acción, entidad, fecha y antes/después.

Los datos sensibles se guardan fuera de htdocs para que Apache no los sirva: .env en ~/.config/secopsentinel/ (chmod 600); expedientes, exportaciones y respaldos en ~/.local/share/secopsentinel/; logs en ~/.local/state/secopsentinel/. Con la decisión de datos cifrados, los datos y secretos deben residir dentro del contenedor LUKS o cifrarse con age/GPG mientras no exista cifrado de disco completo. Un .htaccess en la raíz deniega .git, app, data y .env, y permite solo _fix/. Los documentos originales no se guardan en la base de datos: la BD conserva rutas relativas, SHA-256 y metadatos; el texto extraído sí puede almacenarse para búsqueda FULLTEXT y citas por página.

Flujo técnico del MVP

  1. Cargar denuncia/OPJ: guardar archivo, calcular SHA-256 y crear el trabajo.
  2. Leer: PDF digital con pdftotext/pypdf/pdfplumber; páginas escaneadas con Tesseract y respaldo de visión gemma4.
  3. Extraer: Ollama devuelve JSON validado con personas, entidades, contratos, delitos y evidencia textual, citando página o fragmento.
  4. Alimentar: se crea o actualiza el caso, el expediente, las personas y los contratos en la BD; el Excel se regenera como exportación.
  5. Alertar: reglas y análisis jurídico generan alertas de delitos, términos y documentos faltantes.
  6. Seguir: actividades, oficios, respuestas y vencimientos con estados.
  7. Automatizar: oficios, entrevistas, informes, descarga SECOP y exportaciones.
  8. Indexar: FULLTEXT y búsqueda semántica para relaciones y Copilot.

Reglas de IA

  • Ninguna llamada a APIs pagas; solo 127.0.0.1:11434.
  • Modelo por tarea: gemma4:e4b para visión/herramientas, qwen2.5:7b-instruct para texto/JSON y nomic-embed-text para embeddings.
  • Un solo trabajo de IA a la vez para no saturar los 15 GB de RAM; cola persistente en jobs.
  • Temperatura baja y salida JSON con validación Pydantic y reintento de reparación.
  • Toda extracción debe citar documento y página o fragmento.
  • El investigador confirma antes de persistir; el sistema no decide por el fiscal.
  • Prompts versionados y registro de auditoría de cada análisis.
